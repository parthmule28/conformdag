## Purpose

Specifies the ConformDAG team governance platform per ADR 0003: a Docker
Compose stack (FastAPI API, SPA dashboard, worker, Postgres) that runs the
existing scan engine durably, stores findings history, manages suppressions,
and exposes a stable versioned HTTP API — while the canonical report JSON
remains the export contract and the CLI stays a pure offline tool.

## ADDED Requirements

### Requirement: Workspace file registration

The platform SHALL read a workspace YAML file from an explicit
operator-supplied path, defaulting to `./conformdag-workspace.yaml`. The
workspace file SHALL register local DAG repository paths and the policy pack
path. Relative paths in the workspace file SHALL resolve against the location
of the workspace file, not the process working directory. The platform SHALL
NOT clone, fetch, or sync remote git repositories.

#### Scenario: Default workspace path

- **WHEN** the operator starts the platform without supplying a workspace path
- **THEN** the platform looks for `./conformdag-workspace.yaml`
- **AND** a missing file is a startup error with the checked path in the message

#### Scenario: Relative paths resolve against the workspace file

- **WHEN** the workspace file at `/srv/conformdag/conformdag-workspace.yaml`
  registers `repos/etl` and `packs/org`
- **THEN** the platform resolves `/srv/conformdag/repos/etl` and
  `/srv/conformdag/packs/org`

#### Scenario: No remote git operations

- **WHEN** a registered repository path does not exist on the worker's local
  filesystem
- **THEN** the platform reports a configuration error
- **AND** it does not attempt to clone or fetch the repository from a remote

### Requirement: Durable scan execution

Scans triggered via the platform SHALL run the existing single scan engine
inside a subprocess of the worker process. Job state SHALL be stored in
Postgres such that it survives worker process restarts. The worker SHALL claim
jobs from the queue using row-level locking (`SELECT ... FOR UPDATE SKIP
LOCKED`). Each job SHALL be subject to a timeout, a retry policy, and
cancellation.

#### Scenario: Worker killed mid-scan recovers

- **WHEN** the worker process is killed while a scan job is executing
- **THEN** after restart the job is reclaimed or retried according to its
  retry policy
- **AND** no job is left permanently stuck in a running state

#### Scenario: Scan cancellation takes effect

- **WHEN** an admin requests cancellation of a running scan job
- **THEN** the worker terminates the scan subprocess
- **AND** the job is recorded as cancelled rather than failed

### Requirement: Single scan engine parity

A scan run from the platform SHALL produce the same canonical report JSON
contract as the CLI for the same repository root, policy pack, and
configuration. The platform SHALL NOT implement a second policy evaluation
pipeline.

#### Scenario: Platform scan matches CLI scan

- **WHEN** the same repository root, pack, and configuration are scanned from
  the CLI and from the platform
- **THEN** the canonical JSON report contract is the same (report version,
  findings, policy pack identity)

### Requirement: Stable versioned HTTP API

The platform HTTP API SHALL be served under `/api/v1` and documented via
OpenAPI from the running API process. The `/api/v1` surface SHALL be treated
as a compatibility surface within a major platform version: breaking changes
SHALL require a new major API version. The SPA dashboard SHALL be served as
static assets by the API process; the platform SHALL NOT require a separate
CORS-enabled frontend service.

#### Scenario: API is discoverable and versioned

- **WHEN** an operator or integration opens the OpenAPI document of a running
  platform
- **THEN** all platform endpoints are documented under the `/api/v1` prefix

#### Scenario: Dashboard served from the same origin

- **WHEN** an operator opens the platform in a browser
- **THEN** the SPA is served by the API process from the same origin with no
  cross-origin requests required

### Requirement: Postgres state and canonical report artifacts

Findings history, scan metadata, and suppressions SHALL be stored in Postgres
(normalized findings for query and trends; JSONB artifacts for full reports).
Exports (SARIF, HTML, JSON) SHALL be projections of the stored canonical
report. Exports generated by the platform SHALL NOT differ from the CLI's
exports of the same canonical report. Schema changes SHALL ship as Alembic
migrations.

#### Scenario: SARIF exported from the dashboard matches CLI SARIF

- **WHEN** a scan completed on the platform is exported as SARIF from the
  dashboard
- **THEN** the SARIF is identical to the SARIF the CLI produces for the same
  canonical report

#### Scenario: Schema changes are migrations

- **WHEN** a platform release changes the Postgres schema
- **THEN** the release ships an Alembic migration that upgrades an existing
  deployment without data loss

### Requirement: Single-admin authentication

Mutation endpoints (trigger scan, cancel job, create/edit/expire suppression)
SHALL require admin authentication held by the platform owner. The platform
SHALL NOT provide multi-user accounts or RBAC. Read endpoints MAY be open on
localhost deployments, and the documentation SHALL state the bind posture and
which endpoint classes require authentication.

#### Scenario: Anonymous user cannot edit suppressions

- **WHEN** a request without admin authentication targets a suppression
  mutation endpoint
- **THEN** the request is rejected
- **AND** no suppression state changes

#### Scenario: No RBAC surface

- **WHEN** the platform is deployed as documented
- **THEN** there is exactly one admin principal and no per-user roles to
  configure

### Requirement: Suppression lifecycle management

The platform owner SHALL be able to create, edit, and expire suppressions from
the dashboard. Suppressions SHALL carry audit fields (creator, creation time,
reason, expiry). Suppressed findings SHALL remain visible in the dashboard with
their suppression state; expiry SHALL return the finding to active without
operator intervention.

#### Scenario: Create a suppression from the dashboard

- **WHEN** the platform owner creates a suppression for a finding with a
  reason and expiry
- **THEN** subsequent scans report that finding as suppressed with the
  suppression state visible in the dashboard
- **AND** the suppression records creator, creation time, reason, and expiry

#### Scenario: Expired suppression stops suppressing

- **WHEN** a suppression's expiry time passes
- **THEN** the finding is reported as active again on the next scan
- **AND** the expired suppression remains in the audit history

### Requirement: Compose deployment is the whole product

The documented Docker Compose stack SHALL run the API process, the worker
process, and Postgres as the complete platform. The platform SHALL NOT require
additional stateful services beyond Postgres.

#### Scenario: Compose bring-up yields a working platform

- **WHEN** an operator runs the documented Compose stack with a valid
  workspace file
- **THEN** api, worker, and postgres are up, migrations have run, and journey D
  completes against the dashboard without CLI use

### Requirement: Large-repository operation

The worker SHALL cache per-file parse results keyed on file content hash.
Repeated scans of unchanged files SHALL NOT reparse them. The parse cache
SHALL NOT change scan results: a fully cached scan SHALL produce the same
canonical report JSON as an uncached scan.

#### Scenario: Unchanged files are not reparsed

- **WHEN** a repository is scanned twice with no source changes
- **THEN** the second scan skips parsing of unchanged files
- **AND** both scans produce the same canonical report JSON
