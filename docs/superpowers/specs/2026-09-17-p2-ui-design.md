# P2 Design System And UI Surface

**Status:** Proposed
**Date:** 2026-09-17
**Parent roadmap:** `docs/roadmap.md`
**P1 dependency:** P1 foundation and remediation accepted on `main` at
`bc1afa1`; the final P1 acceptance record is
`.superpowers/sdd/2026-09-16-p1-remediation/acceptance-report.md`.

## Purpose

P2 turns the existing dashboard shell into a complete governance product
experience. A user must be able to understand repository health, inspect a scan,
act on a finding, manage suppressions, edit policy metadata and quality gates,
and navigate directly to any of those states.

P2 is a full-stack slice. The current P1 API and data model provide the durable
state and safe mutation boundaries, but the UI requirements need additive read
endpoints, richer finding queries, gate mutation endpoints, and a policy tag
field. Backend changes remain deterministic and read/write contract work only;
`scan_repository()` remains the sole evaluation pipeline.

## Goals

- Establish a coherent, responsive design system with light and dark themes.
- Replace the single-state dashboard with URL-addressable overview, repository,
  scan, policy, gate, and suppression experiences.
- Give users useful history, trend, baseline, gate, and finding context without
  requiring direct API knowledge.
- Make every supported policy and gate mutation round-trip through the existing
  authoritative pack validation and atomic writer.
- Add Playwright golden journeys that exercise the real browser-to-API contract.
- Preserve every P1 correctness, security, and operational invariant.

## Non-goals

- No v1 release, tag, package publication, or release-train change.
- No dbt check pack, MCP server, report-diff engine, scheduled scans, or
  webhooks; those remain later roadmap slices.
- No semantic/BYOK configuration, OpenAPI redesign, multi-user identity system,
  realtime transport, or general observability platform.
- No new evaluation or policy interpretation path for trends, filters, or UI
  summaries.
- No broad redesign of the scan engine, worker state machine, or policy schema
  beyond the policy `tags` field required by this slice.

## Product Shape

### Visual language

The product is an operations console, not a generic card dashboard. It uses a
dense but calm information hierarchy: strong page titles, compact status
signals, readable tables for repeatable data, and detail panes for evidence and
actions. A single accent color carries interaction state; semantic colors are
reserved for pass, fail, error, warning, and suppression states.

Tailwind v4 CSS-first theme tokens define the type scale, spacing, radii,
surfaces, borders, accents, focus rings, and semantic status colors. The default
theme follows the system preference. A visible theme toggle overrides that
preference and persists locally. Both themes must meet the repository's existing
accessibility expectations: keyboard-visible focus, readable contrast, and no
status communicated by color alone.

The layout must work at desktop and mobile widths. Tables become stacked rows or
horizontal scroll regions rather than disappearing. Actions remain reachable
without hover-only controls.

### Routes

The SPA uses a real URL router and preserves the backend's last-resort static
fallback. The canonical routes are:

- `/` — overview.
- `/repos/:repositoryId` — repository detail and scan history.
- `/scans/:scanId` — scan detail, gate result, issues, and findings.
- `/policies` — policy packs, policy metadata, and gate configuration.
- `/suppressions` — suppression inventory and editing.

Unknown API paths continue to return JSON 404 responses, and unknown browser
paths continue to receive the SPA document through the final StaticFiles mount.

## P1 Contract Rules

Every P2 implementation task is bound by these existing P1 rules:

1. `scan_repository()` is the only evaluation pipeline. Read-only aggregates
   query persisted `ScanRow`/`FindingRow` data; they never re-evaluate policy
   code.
2. `load_policy_pack()` and every pack mutation use the same
   `validate_policy_pack()` authority. A mutation validates the complete
   reconstructed pack before `_write_pack()` and leaves bytes unchanged on
   rejection. This includes policy upsert, policy delete, and gate mutations.
3. Pack YAML is the versioned, git-native source of quality gates. The platform
   stores operational baselines on repositories. The UI must not duplicate gate
   or baseline state in browser storage.
4. An unsuppressed `FindingStatus.ERROR` produces an incomplete report and a
   fatal `EVALUATION_ERROR`. Incomplete reports have `gate_result: null`; every
   UI state must say that gates were not evaluated, never imply a pass.
5. Active platform suppressions are applied before the runner derives the final
   incomplete/error outcome. A matching suppression can waive the corresponding
   finding consistently with repository suppressions; an expired suppression
   cannot.
6. A successful baseline is same-repository, `succeeded`, and `complete is True`.
   The UI must not offer an ineligible scan as a baseline.
7. Startup migrations remain Alembic-owned. P2 adds an additive migration for
   finding end positions only; it must not introduce `Base.metadata.create_all()`
   or runner-owned migrations.
8. New FastAPI routes are registered before the `/api/{rest:path}` fallback and
   the `/` StaticFiles mount. The SPA accesses data only through typed `/api/v1`
   client functions.
9. Python remains Pyright-strict with at least 90% coverage. TypeScript remains
   strict. The ignored static directory remains included in the wheel through
   the existing Hatch artifact rule.

## Backend Contract

### P2 hygiene boundaries

The first backend task closes P1 residuals that become user-facing in this UI:

- `PackService.delete_policy()` validates the full pack after removing a policy
  and rejects a deletion that would leave an `always-block` gate referencing an
  unknown policy. No bytes are written on rejection.
- `GET /api/v1/packs/{pack_name}/policies` maps `PolicyValidationError` through
  the existing structured client-visible validation error path instead of a
  generic 500.
- The API fallback includes `PUT`, so unknown API methods receive the same JSON
  404 behavior as other methods.
- The runner's platform-suppression ordering is corrected so the stored report,
  `complete`, gate evaluation, and UI state agree about waived `ERROR` findings.

### Stable list responses and pagination

The existing scan history and findings routes retain their JSON array body for
compatibility. They accept additive query parameters and return an
`X-Total-Count` response header; CORS exposes that header. Existing callers that
ignore the header continue to work.

`GET /api/v1/repos/{repository_id}/scans` accepts `limit` and `offset`, ordered
by `created_at DESC, id DESC` for a deterministic tie-breaker. Its body remains
an array of scan summaries.

`GET /api/v1/scans/{scan_id}/findings` retains the existing `status` filter and
adds exact filters for `severity`, `policy_id`, `file_path`, `suppressed`, and
`baseline_status`. It accepts `limit` and `offset`, ordered by
`policy_id, file_path, start_line, fingerprint`. Its body remains an array.

The normalized finding payload adds `end_line`, `baseline_status`, and the
existing persisted `fix` payload to the typed client contract. Full evidence,
audit evidence, and runtime details remain available through the canonical
report while that artifact is retained. If the artifact was pruned, the detail
view explicitly shows that the report artifact is unavailable while retaining
the durable normalized finding data.

### Overview and trends

Add read-only aggregation routes:

- `GET /api/v1/overview?days=30` returns repository count, completed scan count,
  active scan count, current unsuppressed failure/error count, current new
  finding count, and daily trend points across registered repositories.
- `GET /api/v1/repos/{repository_id}/trends?days=30` returns daily points for
  that repository.

For the overview's current failure/error/new counts, "current" means the latest
eligible (`succeeded` and `complete is True`) scan for each repository; queued,
running, failed, cancelled, and incomplete scans do not contribute. A repository
without an eligible scan contributes no findings. Each trend point includes its
UTC date, completed scan count, fail finding count, error finding count,
suppressed finding count, and new finding count across scans completed that day.
Counts use the same status and suppression semantics exposed by the findings
route. A missing or ineligible baseline produces no false `new` count. The
endpoints never invoke an evaluator and do not mutate state.

### Gate management

Add typed `PackService` methods and API routes:

- `GET /api/v1/packs/{pack_name}/gates` returns gates in pack order.
- `PUT /api/v1/packs/{pack_name}/gates/{gate_id}` creates or replaces one gate
  from a typed `rules` payload.
- `DELETE /api/v1/packs/{pack_name}/gates/{gate_id}` removes one gate.

All gate mutations run under the existing pack lock, reconstruct the complete
pack, call `validate_policy_pack()`, and only then call `_write_pack()`. Gate
order is preserved for replacement and new gates append. All five existing gate
rule types are supported: `no-new-findings`, `max-severity`, `max-findings`,
`always-block`, and `failure-rate`. Invalid rule shapes, duplicate IDs, and
unknown `always-block` policy IDs return validation errors before any write.

The UI treats `gate_result` as one result selected by the existing evaluator
contract. It renders the gate ID and rule details when present, `not evaluated`
when the scan is incomplete or the artifact is unavailable, and never computes a
replacement result in the browser.

### Policy domain tags

Add `Policy.tags: list[str]` with an empty-list default for existing packs. Tags
are unique, non-empty lowercase slugs matching `[a-z0-9][a-z0-9-]{0,31}`. The
model validator preserves input order after duplicate rejection. Existing YAML
without the field loads as `[]`.

`PolicyUpsertRequest`, `PackService.list_policies()`, the policy API client, and
the generated policy-pack schema all include tags. An omitted update field
preserves existing tags; an explicit empty list clears them. Existing policy
metadata remains lossless through the read-modify-write path. Run
`mise run schema:update` and commit the generated schema after the model change;
`mise run schema --check` is a required gate.

## Frontend Architecture

The SPA remains React 19 + Vite + TypeScript strict + Tailwind v4 + TanStack
Query. The current `App.tsx` is split into route pages, query hooks/client
functions, and focused reusable components. The exact file layout may follow
the existing project conventions, but a page must not duplicate API fetch or
mutation logic.

### Shared components

Create accessible primitives with consistent loading, disabled, focus, error,
and responsive states: `Button`, `IconButton`, `Badge`, `Card`, `Table`,
`Modal`, `Input`, `Select`, `Textarea`, `Tabs`, `Banner`, `EmptyState`,
`Pagination`, and `ThemeToggle`. Components use theme tokens rather than page
specific color literals.

The typed API client exposes structured `ApiError` data containing HTTP status,
request ID when supplied, and parsed detail. Pages map 401, 409, 422, and 503
to actionable messages without exposing raw stack traces. Query invalidation
remains explicit after mutations; active scans retain bounded polling.

### Pages

**Overview**

- Shows aggregate repository/scan/failure/new-finding counts.
- Shows trend points with a clear empty state and no fabricated zero history.
- Shows recent active/completed scans with links to repository and scan detail.

**Repository detail**

- Shows repository configuration, current baseline, and paginated scan history.
- Allows an eligible scan to become the baseline and clearly identifies the
  current baseline.
- Allows triggering and cancelling scans with terminal-state conflict errors
  shown inline.

**Scan detail**

- Shows status, timestamps, completeness, gate outcome, run issues, and runtime
  observations.
- Shows `incomplete` and `gates not evaluated` for incomplete reports, including
  unresolved static evaluation errors.
- Provides findings filters for all server-supported fields, pagination, and
  baseline labels. A finding detail panel shows explanation, remediation, file
  location, fix payload, and retained evidence when available.
- Provides JSON/SARIF/HTML export actions with the existing endpoint contract.

**Policies and gates**

- Groups and filters policies by domain tag, check kind, severity, and lifecycle
  status.
- Edits title, invariant, tags, check configuration, and existing contract
  metadata through the existing lossless policy endpoint.
- Creates, replaces, validates, and deletes gates through the new gate routes.
  Validation errors are attached to the relevant form and never reported as a
  successful save.

**Suppressions**

- Lists active, expired, and source-specific suppressions.
- Creates and edits reason, owner, and expiry.
- Links a suppression to its policy/fingerprint and explains when it is not
  active. An expired suppression is visibly distinct and cannot be presented as
  waiving a current finding.

## Golden Journeys

Playwright is added as a frontend development dependency with a CI job. The
browser suite uses a disposable SQLite-backed platform process and seeded local
repository/pack data; it does not require external providers or live Airflow
containers.

The required journeys are:

1. Load overview → open a repository → inspect history and baseline.
2. Trigger a scan → follow active status → open the completed scan → filter a
   finding → inspect detail.
3. Create a suppression with owner/expiry → confirm it appears and expires in
   the suppression view.
4. Edit policy tags and metadata → validate the pack → observe the saved value.
5. Add or edit a gate → validate the pack → scan → render the returned gate
   result, including the incomplete/no-gate-result state.

The browser tests use real API routes and the same typed client as production;
they do not replace API tests with network mocks. CI runs the existing backend
gates, the SPA build, and the Playwright journeys.

## Testing And Acceptance

Backend changes use strict red → green → refactor TDD. Every new API behavior
has focused tests for success, validation failure, unchanged-on-rejection
behavior, and P1 error semantics. Migration tests use the existing initializer;
no test creates the platform schema through `create_all()`.

The P2 branch is accepted only when:

- `mise run check` passes with Pyright strict and the existing non-runtime suite.
- `mise run test:coverage` passes at or above 90%.
- `mise run schema --check` passes after the Policy model change.
- `mise run test:runtime` passes, including the existing contract/runtime tests.
- `mise run ui-build` and `npm run build` pass with TypeScript strict checking.
- Playwright golden journeys pass in CI and locally with the documented seed.
- Focused tests prove incomplete reports never display or serialize a passing
  gate result, and suppressed `ERROR` findings follow the same state through
  scan, platform, API, and UI.
- Focused tests prove all pack mutations reject invalid reconstructed packs
  before touching bytes, including policy deletion and gate changes.
- The round-trip benchmark remains green, route ordering is preserved, no
  second scan pipeline exists, and no v1 release tag is created.

## Delivery Order

One P2 plan contains these ordered phases, each with its own commit and
independent review:

1. Close the P1 hygiene boundaries and add their regressions.
2. Add the finding-position migration, API pagination/filter contracts, and
   overview/trend aggregates.
3. Add gate CRUD and policy tags, regenerate schemas, and test lossless pack
   mutation.
4. Split the frontend into the tokenized shell, router, typed client, shared
   primitives, and pages.
5. Add Playwright infrastructure and golden journeys, then run the full P2
   acceptance review.

Each phase must continue to use the P1 SDD workflow: implementer, focused
review, fix/re-review loop, full gates, and final whole-branch review. P2 does
not begin until this spec is approved and its detailed implementation plan is
written.
