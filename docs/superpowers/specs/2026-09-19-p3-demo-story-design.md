# P3 Demo Story Design

**Status:** Approved for planning
**Date:** 2026-09-19
**Parent roadmap:** `docs/roadmap.md`
**Dependencies:** P1 foundation and P2 dashboard are complete.

## Purpose

P3 makes ConformDAG understandable in one local command. A prospective user should
be able to launch a realistic governance workspace, follow the enforcement loop in
the dashboard, and understand how a finding moves from policy contract through
scan, remediation evidence, suppression, and export—without Docker, credentials,
or manual data setup.

## Goals

- Add `mise run demo` as the primary, disposable, local product demonstration.
- Seed a coherent, realistic workspace using the production platform, migrations,
  worker, and scan engine.
- Add a guided dashboard tour covering the core governance loop.
- Lead the README with the demo path and its outcome.
- Test launcher behavior, seeded data, and the golden browser journey.

## Non-goals

- The demo is not a replacement for Docker Compose production deployment.
- No mock scanner, alternate evaluator, direct database-only seed path, or second
  platform API is introduced.
- No external provider, GitHub App, agent PR creation, Docker daemon, or network
  dependency is required.
- No new policy check kinds, MCP server, report-diff engine, scheduler, webhooks,
  or changes to the platform's durable production data model are included.
- Tour progress is not an authenticated, shared, or server-persisted feature.

## Runtime and command contract

`mise run demo` starts a local, disposable platform with a temporary workspace and
SQLite database. It invokes the same application factory, Alembic upgrade path,
subprocess worker, and `scan_repository()` evaluation path used by production; it
must not call `Base.metadata.create_all()`, handcraft persisted report records, or
bypass policy-pack validation.

The command runs in the foreground, prints the dashboard URL and local admin-token
posture, and opens the browser by default. It accepts explicit, documented controls
for port selection and browser opening. If its selected port is unavailable, it
fails before startup with an actionable error. Normal shutdown and interrupts stop
children and remove all temporary state. Docker Compose remains the production
deployment method documented in `docs/platform-deploy.md`.

The existing Playwright platform seed process is refactored into reusable,
production-faithful seed primitives. The e2e harness and demo launcher consume those
primitives, so they cannot drift into different schemas or scenario semantics.

## Demo scenario

The seeded workspace represents a data-platform organization and contains enough
real policy, source, scan, and suppression state to make each user-visible concept
concrete:

1. The overview presents repository health and a trend/baseline signal.
2. A repository detail shows a completed baseline and a later scan with actionable
   failures.
3. The later scan shows its quality-gate result and canonical report evidence.
4. A finding identifies its policy contract, source location, and deterministic
   remediation payload.
5. The policy page exposes the governing policy and its relevant gate.
6. The suppression inventory includes both an active, owned, expiring exception and
   an expired exception that is visibly not active.
7. The scan's existing export action demonstrates the portable report artifact.

Seed data is generated by normal platform interfaces and persists only for the demo
process lifetime. It uses stable identifiers exposed through a small demo manifest
or API-derived lookup rather than display-name heuristics, allowing the tour and
browser tests to navigate deterministically as presentation text evolves.

## Guided tour

A compact client-side tour layer is opt-in through the `demo=1` browser query
parameter. The launcher opens that URL; ordinary deployments do not add it. This
keeps demo activation out of the platform data model and API while allowing the
same static bundle to serve both environments. The tour starts on the overview and
takes the user through the seven scenario stages: overview, repository, failing
scan/gate, finding/remediation, policy, suppression, and export.

Each step uses an existing URL route, preserves `demo=1` during tour-controlled
navigation, and has a stable target marker. The tour provides Next, Back, Skip, and
Restart controls, concise explanation, keyboard-accessible controls, and no
color-only instruction. Its state is browser-local: it never changes platform
schemas, API contracts, repository data, or operational user preferences. If a
target fails to render, the tour ends safely with a restart option; ordinary
navigation always remains usable.

## Documentation

The README begins with the one-command demo and a short explanation of what the
user will see. It then presents the usual scan, fix, agent, CI, and deployment
surfaces. The user guide documents demo prerequisites, options, cleanup semantics,
and the distinction between disposable local demo and Docker Compose deployment.

## Testing and acceptance

Python tests prove reusable seed determinism, policy/workspace validity, migration
use, launcher startup and port-conflict errors, and cleanup of child processes and
temporary paths. They also verify that demo scanning flows through the canonical
engine rather than a fixture-only evaluator.

Playwright runs against the real seeded platform and completes the guided narrative:
launch or start state, advance through each stable route/target, verify the finding
and gate evidence, distinguish expired from active suppression, reach export, skip,
and restart. Focused frontend tests cover tour state transitions and missing-target
safe exit. Existing API, worker, migration, and platform tests remain authoritative
for the production components demonstrated here.

## Design invariants

1. `scan_repository()` remains the only evaluation path.
2. Alembic remains the sole platform schema-creation path.
3. The demo consumes the existing typed `/api/v1` contract; no browser code reaches
   directly into Python models or SQLite.
4. The demo has no secret, network, Docker, or external-provider requirement.
5. Seed records, guided-tour navigation, and Playwright assertions use stable IDs
   or explicit target markers—not labels intended for human presentation.
